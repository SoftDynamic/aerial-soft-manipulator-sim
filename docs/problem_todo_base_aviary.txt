一、三架无人机开始时高度完全相同，但目标高度不同。第一个物理时间步后，它们出现了极小的高度差：

    1.736 × 10⁻⁶ 米
    也就是约 0.0017 mm，比头发直径还小很多。
    仓库的下洗公式中有一部分相当于：
    下洗强度∝1/(高度差)^2
    当高度差趋近于零时，分母也趋近于零，结果就会急剧变大：
    计算结果表明：

    单架无人机重量：约 0.265 N
    错误计算出的下洗力：约 616,000,000 N
    下洗力/自重：约 23 亿倍

    一架约27克的无人机显然不可能受到六亿牛顿的下洗力。MuJoCo 收到这个荒谬的力后，加速度爆炸，于是报告：

    Nan, Inf or huge value in QACC

    这类“某个输入接近特殊值，公式结果趋向无穷大”的情况叫作数学奇点或数值奇点。
    将来做多机时怎么办？

            不能只简单地把异常力强行截断，因为“仿真不爆炸”和“物理正确”是两回事。

            未来处理分两层：

            数值安全层
            高度差太小时不使用该公式；
            检查所有力是否为有限值；
            设置合理的力值边界；
            出现异常时明确报错；
            增加多机长期运行测试。
            物理可信层
            查明该经验公式适用的高度和水平距离范围；
            核对公式单位和原始论文；
            用实验数据或可信模型验证；
            必要时换成更合适的尾流模型。

            这会进入未来的“多机功能待办”，但不阻塞当前主线。

三、
        同时 XML 中还有：

        <compiler inertiafromgeom="false"/>

        这是非常重要的一句。它表示：

        不根据几何体自动估算惯量，而是直接使用 <inertial> 中明确填写的质量和惯量。

        因此，那些漂亮的无人机网格模型主要负责显示；圆柱碰撞体主要负责碰撞。它们不会自动改变已经明确指定的机体质量和惯量。

        未来添加软臂时必须特别小心：

        如果软臂是独立刚体，每一段应有自己的质量和惯量；
        如果只是添加可视网格，而没有相应的 <inertial>，它可能看得见却没有正确质量；
        不能只把软臂画出来，还必须建立真实的质量分布。

        不要自己记住“某关节一定在第几个元素”，而要根据关节名称让 MuJoCo 查询。

        MuJoCo 会按照运动树中的关节顺序，把所有关节状态放入统一的 qpos 和 qvel 数组。MuJoCo XML参考

        还要注意：软臂转动关节在 qpos 中保存的是“关节角”，不是软臂末端的世界坐标。末端位置要从对应刚体或 site 的世界坐标读取。
四、 
            
        _getDroneStateVector()

            将单架无人机状态拼成20维向量：

            [
                pos(3),
                quat(4),
                rpy(3),
                vel(3),
                ang_v(3),
                last_action(4),
            ]

            总维数：

            3+4+3+3+3+4=20

            这里同时包含 quat和 rpy，两者表达同一个姿态，因此信息存在冗余。这样做方便使用，但未来设计软臂观测时，需要决定：

            面向传统控制器：可提供结构化完整状态；
            面向强化学习：应谨慎选择是否同时使用 RPY 和四元数；
            不能把“观测向量维数更多”等同于“信息更多”。


            _updateAndStoreKinematicInformation()

                作用是从 MuJoCo 读取每架无人机状态：

                self.pos[i]   = data.qpos中的位置
                self.quat[i]  = data.qpos中的四元数
                self.vel[i]   = data.qvel中的线速度
                self.ang_v[i] = data.qvel中的角速度
                self.rpy[i]   = self._quatToRPY(self.quat[i])

                最后清除：

                data.xfrc_applied[:] = 0

                未来建议把“读取状态”和“清除外力”分成两个函数，因为：

                函数名看起来只是在读取信息，但实际上还修改了物理输入。

                这是一种隐藏副作用，开发时容易踩坑。


五、 _actionSpace()
                VEL和PID的当前风险

                代码在每次预处理动作时执行：

                PIDControl(self).computeControl(...)

                也就是重新创建 PID 控制器。这样可能无法保留：

                位置积分误差；
                姿态积分误差；
                控制器历史状态。

                这是我们之前识别出的“内置PID状态重建”风险。

                开发软臂平台时，初期建议：

                环境保持低级RPM/执行器接口，PID、MPC等有状态控制器放在环境外部并长期保存。
                ATTITUDE

                    这个名字容易让人误解。当前实现只是把指令直接混合成电机RPM，并不是完整的闭环姿态控制器。

                    它没有严格执行：

                    期望姿态 − 当前姿态 → 姿态误差控制

                    因此暂时应把它看作简单动作映射，而不是成熟的姿态控制模式。

            MJC：data.time = 1/240
            DYN：data.time = 0

            step_counter = 1

七、
            当前 BaseAviary._preprocessAction()处理：

            ActionType.PID
            ActionType.VEL

            时，每个控制步都会执行类似：

            PIDControl(self).computeControl(...)

            也就是每一步重新创建控制器。

            结果是：

            积分每一步归零；
            上一次姿态误差丢失；
            不能形成连续的积分和微分状态。

            因此后续平台不能直接照搬这个入口。应该为每架无人机保存一个持久控制器实例，例如：

            self.controllers = [
                PIDControl(self) for _ in range(self.NUM_DRONES)
            ]

            然后重复调用对应实例。
